## Context

ADR-0006 定下的机制是对的：上下文只能由内核组装，每个块都是账本条目，压缩必须是
可见事件而非静默丢内容；ADR-0003 已经给了我们一个无损失的真相（JSONL 事件日志）。
但 ADR-0006 §4 的**压缩动作**仍然是传统形态：

> 越预算 → 先清旧工具输出 → 再 `drop_oldest_exchange()` 丢掉最老的整轮对话。

`drop_oldest_exchange()`（`crates/kernel/src/turn/compaction.rs`）把消息从会话里 `drain`
掉、账本条目 `forget` 掉。前台从此只剩"更短但更模糊"的记忆，而"当时为什么这么设计 /
那个 bug 是怎么查的 / 哪个方案被否决了"这类问题，答案被丢掉的正是最值钱的部分：
**原因与被否决的方案**，恰恰不是可以重新运行命令再生成的东西。原文还在日志里，
但前台没有回到它的路 —— 复现细节只能靠人翻 JSONL。

同时，Claude Code 式的"到阈值才偶发总结"有一个结构性问题：它把**理解**这件事
推迟到最坏的时刻（上下文已经满了、模型已经开始退化、用户正在等），并且每次都要
重读全部历史 —— 成本随历史长度线性增长。

我们想要的形态是：新内容不断产生 → 后台常态、增量地提取与归纳并建立索引 →
**原文始终保留** → 前台只携带少量认知摘要，需要时再定位并恢复细节。

## Decision

**把上下文管理从一种有损压缩机制，改为一种可逆的信息组织机制。**
分四层派生记忆加一个底座，前台只携带最薄的一层，其余按需检索。

1. **检索层与理解层分离**，这是本 ADR 的核心。检索层（原文、L1 原子记录、
   关键词与实体索引）与原文一致、可校验、无模型也可用；理解层（L2 事件摘要、
   L3 模块地图、L4 全局地图）是模型的加工品，**可能错**，必须带引用区间并
   可被取代。产品后果：理解层是可选的（用户选装小模型），检索层**永远开启** ——
   它是"不丢原文"的兑现。用户提出的"是否需要语义归纳"分支，就是这里的开关。

2. **四层，上行收敛。** L4 全局认知地图 / L3 主题·模块地图 / L2 事件·任务摘要 /
   L1 原子事实与局部事件。每层的输入**只是它的直接子层**，不是全文回看：

   ```
   L4 ← 全部 L3 摘要 + 项目级不变量
   L3 ← 该模块的全部 L2 摘要
   L2 ← 一段 L1 区间
   L1 ← 新事件（确定性，无模型）
   ```

   这条规则同时决定了成本与质量都不随历史长度爆炸：L4 每次重算读的是
   "模块数 × 常量"，而不是十万 token 的对话。L1 是**原子记录**（近原文、稳定 ID、
   携带原文定位），不是传统意义上的短摘要。

   **推论（并且是一条硬规则）：增量 ≠ 链式。** 摘要永远从它**当前的子层重新派生**
   （子层已物化的摘要 + 本次新增 L1），**绝不把上一版摘要正文当作自己的输入**去
   "更新一下"。未变的子层摘要在库里，所以成本与"只处理增量"等价，但**误差不累积** ——
   L4 的每个事实都有一个只经过一次归纳的 L2 祖先。若允许 L3 读旧 L3，四层就是四次
   迭代，误差按层数放大且无法归因。代码里用 `summary_inputs`（派生血缘）把这条规则
   做成**可检查**的，而不是靠提示词约束。

3. **原始记录仓库是底座，不是第五层摘要。** JSONL 仍是唯一真相（ADR-0003），
   派生记忆（SQLite）可丢弃、可重建。**每条摘要必须携带引用区间 `[(seq_from, seq_to)]`，
   否则不予物化** —— 摘要不能指向证据，就不是记忆，是幻觉。

4. **模型只做归纳，不做记账；而且是"逐字段"地分工。** 确定性程序负责：工具/路径/命令/
   错误码提取、git diff 与测试结果、稳定 ID、内容哈希去重、按实体建立关联、
   关键词与实体索引、记录时间/来源/版本，以及**所有能算出来的摘要字段**。
   模型负责：把多条事件归纳成任务结论、判断新结论是否**改变**既有认识、
   区分事实/推断/计划/已验证、判断是否值得上行、说出"为什么"与"哪个方案被否决"。
   逐字段归属（`producer` 记得住每一条来自谁）：

   | 字段 | 谁填 |
   |---|---|
   | `status`（done/open/blocked）、`seq_from`/`seq_to`、`citations` | **程序**（测试结果 / commit / pending 批准 / 未决问题是否清空） |
   | `touched_files[]`、`commands[]`、`tests[]` | **程序**（L1 实体与事件种类；`tests` 必须保留"先失败后通过"的转变） |
   | `conclusion`、`rejected[]`、`open_questions[]`、`why[]` | 模型（不可用时留空并标 `degraded`） |

   这条规则的依据是实测而非洁癖：`qwen2.5:3b` 归纳得基本正确时，
   仍把"测试通过并已提交"的 `status` 填成 `open`。**能算出来的字段让模型猜，
   就一定会错，而且错得很难发现。**

5. **两个模式，一套机制。**
   - **R 模式（record，默认回滚路径，零依赖）**：只有检索层 + 确定性 digest。
     现有压缩路径保持原样（清工具输出 + 丢最老交换）。
   - **S 模式（semantic，可选装）**：在 R 之上生成 L2 synthesis / L3 / L4。
     开启后**不再丢弃消息**（本 ADR 对 ADR-0006 §4 的修订点），预算压力下只清工具输出；
     被清掉的工具输出仍然可从日志检索与展开。
   不启用分层引擎时，行为与今天完全一致（这是 owner 明确要的回滚路径）。

6. **摘要是索引，不是事实。** 模型回答关于过去的问题时先 `recall`
   （已实现：只在引擎开启时提供；摘要优先、原文兜底；`expand` 强制同时返回原文；
   整条答案有硬上限且截断时明说；搜不到返回的是一句"没有匹配，但别据此断定什么都没发生"，
   而不是一个错误 —— 返回错误会教会模型"问过去是坏的"）；
   任何"已验证/已修复"的断言必须带 evidence 区间；`recall(expand=…)` **强制同时返回
   原始证据摘录**，不只是摘要正文 —— 从机制上防止摘要被当成真相。发现摘要与原文
   不符时以原文为准，旧摘要标 `superseded_by`，**不静默覆盖历史**。
   **实现状态（2026-10-14）**：`superseded_by` 这一半**没有兑现** —— 过期摘要由
   `replace_overlapping` 删除并重派生（列在、从未写入）。见 Consequences 的"尚未落地"清单。

7. **新内容只处理一次，稳态即休眠。** 每类处理器维护自己的高水位（`watermark`），
   只读水位之后的事件；新事件按实体归入受影响的模块并标脏，只重算脏模块与
   （必要时）L4。每条事件摊还 O(1)，而非每次重读全文。后台在
   `watermark == 尾部 ∧ dirty == ∅ ∧ 无飞行中任务 ∧ 窗口预算用尽` 时休眠，
   由新事件/新 turn/工具等待/显式请求唤醒。

8. **不与前台争抢资源。** 单飞行（同一时刻最多一个归纳请求）、每空闲窗口的
   `window_calls`/`window_tokens` 硬预算、前台新 turn 立即让出、默认单线程并降低优先级。
   优先安排在工具调用等待、模型思考间隙与空闲时运行 —— 不为"实时总结"阻塞任何人。

9. **存储尽量简化。** 每会话一个 sidecar SQLite（`<session>.context.db`），
   表：`watermark` / `atom` / `entity` / `atom_entity` / `summary` / `citation` /
   `summary_entity` + 摘要全文检索。删掉它零损失（只损失已花掉的归纳成本）。
   一个会话一个写者；WAL。

10. **摘要的可靠性靠机制，不靠提示词。** L2 synthesis 的必填字段包含
    `rejected[]`（被否决的方案）与 `open_questions[]`，因为压缩最容易、也最不该
    丢掉的正是这两类信息；L4 有 token 上限（默认 400）；每层都有 `status`、
    `schema_ver`、`producer`。

11. **可见性不降级。** L4 以新的 `Category::CognitiveMap` 条目进入账本（pinned，
    session 生命期，允许原地 `replace`）。`ContextExplain` 增加：各层条数与 token、
    记忆模式与降级原因、worker 状态（窗口/模型调用次数/待富化/失败）。
    "为什么这句话在我上下文里"必须仍然是一个查询。
    **实现修正（2026-10-14）**：`recall` 的结果**不另记** `Category::Retrieval` 条目 ——
    答案本身就是一条 `tool.result` 历史消息，再记一条会把同一批字节双重计入上下文预算；
    `Category::Retrieval` 这个分类仍在枚举里，只是不由 `recall` 使用。

## Alternatives considered

- **维持现状（只在阈值处更聪明地压缩）**。拒绝：丢掉的"原因与被否决方案"不能
  靠重跑命令恢复；成本仍随历史线性增长；前台一旦变浅就再也没有回去的路。
- **只做后台增量总结，仍用总结替换原文**。拒绝：这仍然是有损压缩，只是提前了。
  它省 token 但把"可逆"这一条丢了，而可逆才是这套设计真正要买的东西。
- **让主模型（远端强模型）做后台归纳**。拒绝：成本与延迟都不可接受，且与
  "可选装"的语义冲突 —— 归纳是高频小任务，不该占用最贵的资源。
- **只做向量检索，不做分层摘要**。拒绝：向量检索解决"找得到"，不解决
  "前台应该携带什么认知"。而且主路径必须是可解释、可用 `grep` 式行为验证的；
  向量检索作为后续可选增强。
- **跨会话自动共享记忆**。不在本 ADR：与 ADR-0010 的立场（知识走 git、不进共享会话）
  冲突，需独立 ADR。
- **把 L3 的模块归属交给模型决定**。拒绝：归属必须是确定性规则（路径/符号/任务 ID），
  否则"脏集合"无法计算，成本不可控、不可测试。模型写内容，不选位置。

## Consequences

- **ADR-0006 §4 被修订**：压缩顺序（先清工具输出）保留；"再丢最老交换"在引擎开启时
  被**禁用**，改为"原文留在日志、前台由 L4/L3 承载、`recall` 负责回填"。
  引擎关闭时 ADR-0006 §4 原样有效 —— 并且这一点是**对照测试**保证的，不是承诺：
  同一个长会话在引擎关闭时 `dropped_messages >= 1`，开启时为 `0`。
- **前台常驻的只有 L4**（硬上限 400 token，作为一条独立的 system 消息置于系统提示
  之后，通过 `Ledger::replace` 原地刷新，全程只有一条账本条目）。L3/L2 走 `recall`
  按需 —— 常驻 L3 会让"最浅表上下文总是最精简"从一开始就不成立，因为 L3 的数量
  随模块数增长而 L4 的边际成本是常数。
- **一个新的 crate**（`loong-context`，已落地）承载引擎；内核只通过只读接口取 L4 与
  检索结果，摘要不参与内核决策逻辑 —— 保持 ADR-0004 的固定核心。
  P1（L1 物化 + 实体/关键词索引 + 增量水位 + `rebuild`/`verify`）、P2（确定性 L2
  digest、引用与派生血缘、`recall`/`expand`）、P3（字节 tail、增量 `sync`、
  `digest_pending` 补积压、前台让出 + 预算的 worker）、P4（L3 域地图、L4 全局
  地图、内核 `Category::CognitiveMap` + `Ledger::replace` + `refresh_map`、
  引擎开启时不丢弃任何交换）以及 P5 的**机制部分**（`Summarizer` trait、Ollama 原生
  客户端、`Store::synthesize` 的纯增量合并、忠实度门槛）已实现并通过全部门禁。
  配置开关也已接线：`[context_engine]` / `[summarizer]` 由 `loong-config` 解析，
  两个 `enabled` 以 0/1 narrow-only 数值参与合并（`0` 更严格），因此**企业层可以强制关闭、
  用户层无法放宽**；`summarizer.base_url`/`model` 是端点键，仓库层被拒。
  缺省即关：没有任何一层说过它，就按改造前的行为走。内核的 `ContextEngine::refresh`
  在确定性派生之后**只唤醒后台**，不再调用 summariser —— 模型调用在一条独立线程上按
  空闲窗口（`window_calls`/`window_tokens`）批量进行，用第二个 `Store` 连同一个 sidecar，
  整轮前台 busy 时让出。**P3 的两条实测**：空闲查看 27 µs；向 2.1 MB 日志追加一个任务后
  同步 + 派生 8.4 ms（修掉一次"每次 digest 扫全部摘要"的 O(历史) 退化之前是 57 ms）。
  **P5.5 的两条实测（2026-10-14）**：前台 6 次步边界（24 任务，确定性派生）共 17–19 ms，
  而同一模型调用若在前台单次就要 301 ms；一次空闲窗口（7B、4 calls/6000 tokens）富化
  4 段，窗口 1 10.44 s（含模型加载）、窗口 2 5.50 s，合计 15.94 s / 8 段（重跑 ~16.1 s，
  模型延迟有波动）。
  验收门禁是结构性的：`refresh_never_calls_the_model`。
  `ContextExplain` 新增 `memory_mode`/`memory_summarizer`/`memory_degraded`/
  `memory_layers`/`memory_worker`，TUI 据此显示开/关、模式、各层条数、worker 统计与
  降级原因 —— **"关着"与"刚开还没产出"是两种显示**。
- **新增事件种类**（schema 先行，`scripts/gen-schema.py` 生成）：
  `memory.l1.materialized`、`memory.summary.updated`、`memory.superseded`、
  `memory.worker.state` —— 后台工作与摘要变更都是可见事件，本 ADR 的承诺才可审计。
  **实现状态（2026-10-14）：一个都还没有。** `protocol.toml` 里没有 `memory.*` 事件，
  引擎也从不写日志（它只读会话日志、只写 sidecar）：水位在 `meta`、摘要在 `summary`、
  worker 统计在进程内。**"摘要变更可审计"这条承诺尚未兑现**，列在设计文档 [§11.1](../context/status.md)。
- **两处尚未落地的机制（2026-10-14 审计发现，如实列出）**：
  1. **`superseded_by` 从未被写过。** 过期摘要当前由 `replace_overlapping` **删除**并
     重派生，而不是"标 `superseded_by` 保留历史"（Decision §6 的后半句没兑现）。
  2. **配置并未全部接线。** `[context_engine] l4_max_tokens` 与 `episode_events` 会被解析
     但无人读取（L4 上限与切段阈值仍是常量）；`store`/`episode_gap_secs`/
     `domain_rollup_episodes`/`recall_limit`/`recall_max_tokens`/`model_fast`/`think`/
     `timeout_ms`/`on_error` 则会被 `deny_unknown_fields` 直接拒绝。详见设计文档 [§11](../context/config.md)。
  3. **`nice`/线程优先级未做**（§8 的"可选"一条）；单线程已实现。
- **成本是可解释的**：每条摘要都有 `producer` 与引用，模型调用次数是可见计数；
  "这个会话为记忆花了多少"是一个查询。
- **主要风险是漂移**：越高层越抽象，越可能偏离事实。对策是上行只读子层、强制引用、
  `superseded_by`、`expand` 带原文；但**必须实测**（见下）。
- **磁盘增长**是真实成本：约等于日志正文 + 摘要。可接受，但需要 `vacuum`/
  保留策略与实测数据。
- **前台可能变浅而模型不自知**：靠系统提示的纪律（先 `recall`、断言带引用）
  与 `expand` 的强制原文来兜底；这需要真实会话上的验证，不能只在单元测试里成立。
- **未定项（本 ADR 不假装已经决定）**：
  1. ~~小模型后端~~ **owner 已定：本机 Ollama（2026-10-13）**。`qwen3:0.6b` 已在本机运行
     （Ollama 0.40.3，Q4_K_M，522 MB，40960 上下文，支持 thinking）。据此定下：

     - **传输层 `kind = "ollama"`（原生 `/api/chat`）**，`think = false`，`format` 传 JSON schema。
       实测 `/v1/chat/completions` **会忽略 `think:false`**：推理过程进 `reasoning` 字段并计入
       `completion_tokens`，200 token 预算被推理链吃光、`content` 只剩半句 ——
       所以现有的 `providers::OpenAiCompat` **不能**直接复用（它没有 `think` 开关）。
     - **两个档位**：synthesis 默认 `qwen2.5:3b`（本机亦有），`qwen3:0.6b` 作快档/降级。
     - **不引入任何新 Rust 依赖**（`loong-http` 已够），二进制零膨胀；
       用户侧只需 `ollama pull`，未装 = R 模式、一切仍可用。
     - **本机实测性能**：0.6B decode ≈257 tok/s、prefill ≈5 400 tok/s；3B decode ≈93 tok/s、
       prefill ≈1 660 tok/s。3B 一次归纳约 **1–3 秒** —— **延迟不是约束**，不必为速度用 0.6B。
     - **能力边界（实测，直接改写实现）**：0.6B **不能**从原始事件清单里提取结构
       （会把事件整段复述进 `rejected[]`、乱填 `status`）；但把输入换成**已归纳的事实句**、
       只问单点语义（"哪个做法被否决、为什么"）时一次答对。⇒ digest 必须由程序先做
       （Decision §4），**给模型的输入质量比模型大小更决定成败**。
     - 内置推理（`llama-cpp-2` 可选 feature / `candle` spike）**不是前置条件**，可无限期推后；
       若将来要做，候选模型为 Qwen3-0.6B（Apache-2.0，397 MB Q4 / 639 MB Q8）、
       MiniCPM5-1B（688 MB，candle 不支持）、Qwen2.5-1.5B（1.1 GB）；
       ⚠️ Gemma / Llama / LFM 系许可证非 OSI，企业内工具建议排除。
  2. ~~CJK 关键词索引方案~~ **已实测定案（待 owner 确认）**：摘要上用 FTS5
     `tokenize='trigram'` 的**外部内容表**（MATCH 与 LIKE 都可用），原文走 `LIKE` +
     实体/工具/kind 精确过滤；**不对原文建全文索引** —— trigram 索引实测达
     208% 原文体积、库总计 318%，与"存储尽量简化"冲突。两条实测否定：
     `detail=none` **只支持恰好 3 字查询**（4 字以上报错），`contentless` 表
     **不能配 LIKE 兜底**（除 rowid 外列读出为 NULL）。短于 3 字符的中文词由应用层
     逐词降级为 `LIKE`（2 万行 5.1 ms），**绝不把 <3 字的词交给 MATCH** —— 混进去会让
     整条查询静默返回 0。不引入中文分词字典；不够快再加 char-unigram 派生列；
  3. ~~摘要全文索引~~ **已实测定案（2026-10-13）：不建**。4 000 条摘要下 LIKE
     扫描 3.8–5.6 ms、FTS5 MATCH 0.12 ms，都远低于可感知量级；而外部内容 FTS5
     带来一整类正确性陷阱（按 rowid 查询会从正文表回答；对未索引的 rowid 执行
     delete 报 `database disk image is malformed`；每次写入要手工同步）——
     实现期间每一个都真的踩到了。测量留在 `tests/search_cost.rs`，
     摘要数量涨到扫描真的变慢时，那份数据就是推翻它的依据。
     原文层同理，从未建过全文索引（trigram 索引达原文 208% 体积）。

  ②`loong context verify` 校验所有引用区间有效、且每条摘要的派生血缘满足 §2 的
  "不许链式总结"（可机械检查）；③删库重建后 `recall` 结果一致；
  ④有测试证明后台 worker 不延长 turn 的墙钟时间；⑤在真实长会话上测

  `crates/context/tests/faithfulness.rs`：10 份真实中英 digest + 已知 ground truth
  （被否决项 / 未决问题 / 状态 / 何时该保持沉默），打分器本身有 gate 测试，
  真机测量是 `#[ignore]` 的 measurement。
  **实测结果推翻了"越大越好"的直觉**：`qwen3:0.6b` 编造 0 次、漏 7 次、说不出原因 2 次；
